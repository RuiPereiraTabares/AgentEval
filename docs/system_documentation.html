Agentic Insight Engine

A multi-agent LLM pipeline that evaluates whether Microsoft support articles adequately address customer support cases. Ten specialized agents collaborate through an orchestrated pipeline to score articles, evaluate AI response quality, assess citation grounding, identify documentation gaps, and classify transfer reasons.

10 Specialized Agents Kepner-Tregoe Framework Weighted Scoring Multi-Provider LLM

Agent Directory

Each agent inherits from BaseAgent and follows a consistent pattern: call the LLM with a specialized prompt, parse the JSON response, and fall back to heuristics if the LLM call fails.

Pipeline Flow

The Orchestrator coordinates agent execution in the following sequence. Each step feeds outputs to downstream agents.

1

Parse Issue

IssueParserAgent.evaluate(customer_issue, product_info) → structured Issue object. Transfer metadata (transferred, sr_status, reopened) is injected from CSV.

2

Evaluate Description Quality

DescriptionQualityAgent.evaluate(issue) → KT framework analysis. If score < 40, sets evaluation_reliability_warning = True.

?

Branch: Has Article URL?

The pipeline branches based on whether the input case contains article URLs (citations).

Path A — No Citation
SearchAgent generates recommended search queries
GapAnalysisAgent identifies documentation gaps (no prior evaluation data)
TransferReasonAgent classifies with contains_citations=False
Result: verdict="no_citation_provided", score=0, action="find_better_article"
Path B — Has Citation(s)
ArticleFetcher fetches each URL (HTTP GET, BeautifulSoup parsing, 30s timeout)
For each valid article, run the scoring triad in sequence:
① RelevanceAgent → RelevanceResult
② CompletenessAgent → CompletenessResult
③ ValidityAgent → ValidityResult
The best overall score across all URLs is selected.
3

Search (Conditional)

If best_score < 70: SearchAgent.evaluate(issue, best_score) generates search recommendations.

4

Gap Analysis (Conditional)

If best_score < 60: GapAnalysisAgent.evaluate(issue, relevance_result, completeness_result, validity_result) identifies documentation gaps.

5

Verdict & Action

ScoringUtils computes the overall verdict and action required based on score, relevance verdict, and search results.

6

Transfer Reason Classification (Always Last)

TransferReasonAgent.evaluate(...) runs with all evaluation data. Uses a cascading decision tree to classify the transfer reason.

✓

Output EvaluationResult

The final EvaluationResult is written to CSV and/or JSON with all scores, verdicts, recommendations, and transfer analysis.

mweaeval (Citation Quality) Pipeline

The evaluate_with_citations() flow is used when AI response text and cited articles are available. It evaluates citation grounding and overall AI response quality in addition to the standard description quality and transfer analysis.

1

IssueParserAgent

Parse raw customer issue into a structured Issue object. 1 LLM call.

2

DescriptionQualityAgent

Evaluate issue description quality using the Kepner-Tregoe framework. 1 LLM call.

3

CitationQualityAgent

Evaluate whether each cited article supports the AI response claims. N LLM calls (one per citation). Produces CitationQualityResult with per-citation verdicts and overall_grounding_score.

3b

R/C/V on Best-Grounding Citation

Run RelevanceAgent, CompletenessAgent, and ValidityAgent on the citation with the highest grounding score. +3 LLM calls.

4

ResponseQualityAgent

Evaluate AI response quality across response quality (40%), groundedness (30%, reused from step 3), and issue resolution (30%). 1 LLM call. Produces ResponseQualityResult with composite ai_response_quality_score.

5

LLM Synthesis

Synthesize all agent results into a structured recommendation with priority, root cause, and PM actions. 1 LLM call (falls back to auto-computed values on failure).

✓

Output EvaluationResult

Final result includes citation grounding scores, AI response quality dimensions, LLM-synthesized recommendations (priority, PM actions, root cause), plus all standard evaluation fields. Written to CSV / JSON.

Total LLM cost per case: 1 (parser) + 1 (description) + N (citations) + 3 (R/C/V) + 1 (response quality) + 1 (synthesis) = N + 7 calls, where N is the number of citations.

Scoring Guide

This section provides a detailed explanation of every score produced by the system, what each score measures, how to interpret it, and what constitutes a high or low score. All scores use a 0–100 scale.

Article Evaluation Scores

These three scores evaluate the quality of a cited support article against the customer's issue. They are combined into a weighted Overall Article Score that drives the system's verdict and recommended action.

1. Relevance Score — Weight: 40% of Overall Article Score

What it measures: How well the cited article matches the customer's specific issue — does the article actually talk about the same product, the same problem, and the same context?

Key evaluation criteria:

  • Product match — Does the article discuss the correct product (e.g., Exchange Online vs Exchange Server)?
  • Version match — Is the article written for the correct version or edition?
  • Matched aspects — Which aspects of the customer's problem are covered by the article?
  • Unmatched aspects — Which aspects of the problem are not addressed?
  • Outdated flag — Is the article's solution based on deprecated features or old versions?

How to interpret the score:

85–100Excellent — The article directly addresses the exact issue. Product, version, and symptoms all match. The customer can follow this article and it speaks to their specific problem.
70–84Good — Most aspects of the issue are covered. The article is about the right product and problem area, but may miss a secondary symptom or a specific environmental detail.
50–69Partial — The article is related to the issue but has significant gaps. It might cover the right product but address a different error, or cover a related scenario that doesn't quite match.
30–49Poor — The article is only tangentially related. It might mention the same product family but addresses a completely different problem or scenario.
0–29Irrelevant — The article does not match the customer's issue at all. Wrong product, wrong problem, or entirely unrelated content.

2. Completeness Score — Weight: 30% of Overall Article Score

What it measures: Whether the article provides sufficient, well-structured information to actually solve the customer's problem — not just whether it's relevant, but whether it contains all the information needed.

Key evaluation criteria (5 aspects):

  • Prerequisites — Does the article list required setup, permissions, or preconditions?
  • Step-by-step instructions — Does it provide ordered resolution steps the customer can follow?
  • Examples / Screenshots — Are there code samples, command examples, or visual aids?
  • Troubleshooting guidance — Does it address common issues, alternative paths, or "what if this doesn't work"?
  • Success criteria — Does it explain how to verify the fix worked?

How to interpret the score:

90–100Complete — All five aspects are present. The article is a comprehensive guide: it tells you what you need before starting, walks you through each step, shows examples, covers edge cases, and tells you how to verify success.
70–89Mostly Complete — Minor gaps only. For example, the article has great step-by-step instructions and examples but doesn't explain how to verify the fix, or lacks a troubleshooting section for common issues.
50–69Incomplete — Significant gaps. The article covers the general topic but is missing key sections like step-by-step instructions, or provides steps without any troubleshooting guidance or examples.
0–49Severely Lacking — The article is a stub or overview with insufficient content. It may describe the problem but provides little to no actionable guidance for resolution.

3. Validity Score — Weight: 30% of Overall Article Score

What it measures: Whether the solution described in the article would actually work if the customer followed it — is it technically correct, up-to-date, and compatible with the customer's environment?

Key evaluation criteria:

  • Addresses root cause — Does the solution target the actual problem, or just address symptoms?
  • Is current — Is the solution based on current features, not deprecated APIs, retired portals, or renamed services?
  • Environment compatible — Would the solution work in the customer's specific environment (cloud vs on-prem, specific OS, specific license tier)?

Additional output: The agent also provides a confidence_level (high / medium / low) indicating how certain it is about the validity assessment, and a potential_issues list of concerns.

How to interpret the score:

80–100Valid — The solution is correct and current. It addresses the root cause, uses up-to-date methods, and is compatible with the customer's setup.
60–79Likely Valid — The solution probably works but there are minor concerns. For example, it might reference an older admin center UI that has since been updated, or the solution is generic enough to work but isn't tailored to the customer's specific edition.
40–59Uncertain — Questionable effectiveness. The solution may have worked at some point but it's unclear if it applies to the current environment, or it targets symptoms rather than root cause.
20–39Likely Invalid — The solution probably won't work. It may reference deprecated features, target the wrong environment, or propose steps that are no longer available.
0–19Invalid — The solution is incorrect or completely deprecated. Following it would not resolve the issue and could potentially cause additional problems.

4. Overall Article Score — Composite

What it measures: A single weighted score that combines Relevance, Completeness, and Validity to produce an overall assessment of how well an article serves the customer's needs.

overall_score = relevance × 0.40 + completeness × 0.30 + validity × 0.30

Why Relevance is weighted highest: An article that scores perfectly on completeness and validity is still useless if it's about the wrong problem. Relevance ensures the article is actually about what the customer needs before evaluating its content quality.

How to interpret the score:

≥ 70Adequate — The article is good enough to help the customer (provided relevance is also "excellent" or "good"). No additional action needed.
50–69Needs Supplementation — The article has value but isn't sufficient on its own. The agent should add context, provide additional steps, or find a better article.
< 50Inadequate — The article fails to address the customer's needs. A better article must be found, or new content must be created.
Special case: Even if the overall score is ≥ 70, the verdict can still be needs_supplementation if the relevance verdict is only "partial", "poor", or "irrelevant" — indicating the article scores well on content quality but for the wrong problem.

Description Quality Scores (Kepner-Tregoe Framework)

These scores evaluate the quality of the customer's issue description — not the article. A well-structured problem statement enables more accurate evaluation of articles. The system uses the Kepner-Tregoe (KT) Problem Statement framework, which breaks a problem description into four dimensions.

5. KT Identity Score — WHAT — Weight: 35% of Description Quality

What it measures: Clarity on what the problem is — has the customer clearly identified the product, feature, symptom, and error?

What makes a high score (80–100): The customer names a specific product (e.g., "Exchange Online"), identifies the affected feature (e.g., "mail flow rules"), provides a clear symptom (e.g., "emails are being silently dropped"), and includes error codes (e.g., "NDR 5.7.1").

What makes a low score (0–39): Vague descriptions like "email isn't working" or "something is broken" with no product name, no error codes, and no clear symptom description.

Why it matters most (35% weight): Without knowing what the problem is, it's impossible to evaluate whether an article addresses it. This dimension has the highest weight because it's the foundation of all downstream evaluation.

6. KT Location Score — WHERE — Weight: 25% of Description Quality

What it measures: Clarity on where the problem occurs — the environment, server, region, module, URL, or specific page.

What makes a high score (80–100): The customer specifies the exact environment (e.g., "Azure AD tenant contoso.onmicrosoft.com"), deployment type (e.g., "hybrid Exchange with on-prem AD"), region (e.g., "EMEA datacenter"), or specific URL/page where the issue appears.

What makes a low score (0–39): No environment details at all. The customer doesn't mention whether they're using cloud or on-premises, what tenant or server is affected, or any contextual location information.

7. KT Timing Score — WHEN — Weight: 20% of Description Quality

What it measures: Clarity on when the problem started and its temporal pattern — is it continuous, intermittent, or triggered by a specific event?

What makes a high score (80–100): The customer provides a specific start date (e.g., "started on March 15, 2026"), identifies the pattern (e.g., "intermittent, happens 3-4 times per day"), and describes any triggering event (e.g., "started after we migrated to Exchange Online").

What makes a low score (0–39): No temporal information. The customer doesn't say when it started, whether it's always happening or sometimes, or whether anything changed before it began.

8. KT Magnitude Score — EXTENT — Weight: 20% of Description Quality

What it measures: Clarity on the scale and scope of the problem — how many users, systems, or processes are affected, and what is the trend?

What makes a high score (80–100): The customer quantifies the impact (e.g., "200 users in the EMEA office are affected"), describes the scope (e.g., "all Exchange Online mailboxes on Plan E3"), and indicates the trend (e.g., "the number of affected users is growing daily").

What makes a low score (0–39): No indication of how widespread the problem is. The customer doesn't mention whether it affects one user or thousands, one server or the entire tenant.

9. Description Quality Score — Composite

What it measures: A single weighted score that combines all four KT dimensions to assess how well-structured the customer's issue description is.

description_quality = identity × 0.35 + location × 0.25 + timing × 0.20 + magnitude × 0.20

How to interpret the score:

80–100Well Defined — The issue description is clear, specific, and structured. All four KT dimensions are well covered. The system can evaluate articles with high confidence.
60–79Mostly Defined — Adequate description with minor gaps. Most KT dimensions are addressed but one or two could be more specific.
40–59Partially Defined — The description is missing key information. Multiple KT dimensions are vague or absent, making it harder to accurately evaluate articles.
0–39Poorly Defined — The description is too vague or incomplete for reliable evaluation. The system sets evaluation_reliability_warning = True to flag that all downstream scores may have reduced accuracy.
Reliability Warning: When the description quality score falls below 40, the system flags evaluation_reliability_warning = True on the entire evaluation result. This warns consumers that the article evaluation scores (relevance, completeness, validity) may be less reliable because the system had insufficient information about the customer's actual problem to evaluate articles accurately.

AI Response Quality Scores (mweaeval mode only)

These scores evaluate the quality of the AI-generated response given to the customer. They are only computed in the mweaeval pipeline mode, where the system has access to both the AI response text and the cited articles.

10. Response Quality Score — Weight: 40% of AI Response Quality

What it measures: The overall quality of the AI response itself — is it accurate, complete, clear, helpful, and professional?

Key evaluation criteria:

  • Accuracy — Is the technical information in the response correct?
  • Completeness — Does the response cover everything the customer needs to know?
  • Clarity — Is the language clear, professional, and easy to follow?
  • Actionability — Does the response include concrete steps or guidance the customer can act on?
  • Tone — Is the response written in an appropriate customer support tone?

How to interpret the score:

80–100Excellent — High-quality, specific, actionable response tailored to the customer's issue. Clear steps, correct technical details, professional tone.
60–79Good — Mostly helpful with minor gaps. Could be more specific, or may include some generic advice alongside targeted guidance.
40–59Fair — Partially relevant but with significant gaps. The response may be too generic, miss key aspects of the problem, or lack actionable steps.
0–39Poor — Largely unhelpful. The response may focus on the wrong issue, provide incorrect information, or lack meaningful guidance.

11. Groundedness Score — Weight: 30% of AI Response Quality

What it measures: How well the cited articles actually support the claims made in the AI response. This is the bridge between citation quality and response quality — it checks whether the response is "grounded" in the evidence provided by the citations.

How it works: This score is inherited from the CitationQualityAgent's overall_grounding_score (no additional LLM call). It represents the aggregate grounding across all citations.

How to interpret the score:

70–100Well Grounded — The claims in the AI response are strongly supported by the cited articles. The citations provide substantive evidence for the technical advice given.
50–69Partially Grounded — Some claims are supported by citations, but others are not backed by the referenced articles. The response may contain advice that goes beyond what the citations actually say.
25–49Poorly Grounded — Weak citation support. Most claims in the response are not substantiated by the cited articles. The citations may be tangentially related but don't actually back up the specific advice given.
0–24Ungrounded — The citations do not support the response. The AI may have cited articles that are about a different topic or that contain different technical guidance than what was provided.

12. Issue Resolution Score — Weight: 30% of AI Response Quality

What it measures: Whether the AI response actually addresses the customer's specific issue — not just whether it's well-written, but whether it targets the right problem.

Key evaluation criteria:

  • Does the response directly address the customer's reported problem?
  • Are the suggested actions likely to resolve the specific issue?
  • Does the response acknowledge the customer's context (product, environment, error)?
  • Would a support agent find this response helpful for resolving the case?

How to interpret the score:

80–100Excellent — The response directly targets the reported issue with relevant, specific steps. It acknowledges the customer's environment and error, and provides actionable resolution guidance.
60–79Good — Mostly addresses the issue with minor gaps. The response is on-topic but may miss a secondary aspect of the problem or provide slightly generic advice for one of the steps.
40–59Fair — Partially relevant. The response addresses the general problem area but misses the specific issue, or provides generic guidance that isn't tailored to the customer's situation.
0–39Poor — Wrong focus or largely irrelevant. The response may address the wrong product, error, or scenario, providing guidance that won't help resolve the customer's actual issue.

13. AI Response Quality Score — Composite

What it measures: A single weighted score that combines Response Quality, Groundedness, and Issue Resolution to produce an overall assessment of the AI response.

ai_response_quality = response_quality × 0.40 + groundedness × 0.30 + issue_resolution × 0.30

Why Response Quality has the highest weight: The overall quality of the response (accuracy, clarity, actionability) is the most important factor. Groundedness and Issue Resolution serve as checks that the response is evidence-based and on-target.

How to interpret the score:

80–100Excellent — A high-quality, well-grounded, issue-resolving response. The AI provided accurate, actionable guidance backed by cited evidence and targeted at the customer's specific problem.
60–79Good — An adequate response with minor gaps. It's generally helpful and mostly supported by citations, but could be improved in specificity, grounding, or issue targeting.
40–59Fair — The response has notable weaknesses. It may be partially helpful but suffers from weak citation support, generic advice, or incomplete issue coverage.
0–39Poor — An inadequate or unsupported response. The AI response either provides wrong information, is not backed by citations, or fails to address the customer's actual issue.

Citation Grounding Scores (mweaeval mode only)

These scores evaluate whether individual cited articles actually support the claims made in the AI response. The CitationQualityAgent makes one LLM call per citation to assess grounding.

14. Per-Citation Support Score — Per citation

What it measures: Whether a single cited article supports the specific claims attributed to it in the AI response.

Evaluation logic: The LLM reads the AI response and the full text of the cited article, then determines whether the article actually contains information that backs up the claims the response makes while referencing that citation.

How to interpret the verdict:

goodScore 70–100 — The article substantively supports the claims. The technical steps, commands, or guidance cited from this article are actually found in the article content. Paraphrased content counts as long as meaning is preserved.
partialScore 40–69 — The article partially supports some claims but misses others. The article may cover the general topic but doesn't contain all the specific technical details cited in the response.
badScore 0–39 — The article does not meaningfully support the cited claims. It may be a generic product page that merely mentions the product but doesn't contain the specific guidance attributed to it.

15. Overall Grounding Score — Aggregate

What it measures: The aggregate grounding quality across all citations in the AI response.

How it's calculated: Aggregated from all per-citation scores. Also tracks cited_percentage (portion of the response that references citations) and uncited_percentage (portion without citation support).

How to interpret the score:

70–100Well Grounded — Most or all citations provide strong support. The AI response is well-evidenced.
50–69Partially Grounded — Mixed citation quality. Some citations are strong, others are weak or irrelevant.
25–49Poorly Grounded — Most citations are weak. The response makes claims that aren't well-supported by the referenced articles.
0–24Ungrounded — Citations provide negligible support. The referenced articles don't back up the response content.
Reuse: The overall grounding score from the CitationQualityAgent is directly reused as the "Groundedness" dimension (score #11) in the AI Response Quality composite score, avoiding redundant LLM calls.

LLM Synthesis Outputs

The synthesis step produces actionable outputs for SPMs rather than numeric scores. It runs after all evaluation agents and uses their combined results to generate a structured recommendation.

16. Synthesis Priority — Traffic-light indicator

What it measures: How urgently the SPM needs to act on this case — a single traffic-light signal derived from all agent scores, article quality, and citation grounding.

redImmediate action — The article is inadequate, no citation was provided, or there is a critical content gap. The SPM should prioritize finding or creating appropriate documentation.
yellowImprovement needed — The article partially addresses the issue but needs supplementation, the response has quality concerns, or citation grounding is weak. The SPM should review and improve.
greenNo action needed — The article adequately addresses the customer's issue with good relevance, completeness, and validity. No SPM intervention required.

17. Root Cause Category — Categorical classification

What it measures: The primary reason why the current article or response is insufficient, enabling SPMs to take targeted corrective action.

adequateNo issues — article and response are sufficient
content_gapThe article lacks critical information needed to resolve the issue
wrong_citationThe cited article addresses a different problem or product
poor_descriptionThe customer's issue description is too vague for accurate evaluation
article_outdatedThe article references deprecated features or old versions
citation_quality_lowCitations don't support the claims in the AI response
response_quality_lowThe AI response itself has quality issues (inaccurate, unclear, unhelpful)
no_contentNo article was cited at all

18. PM Actions — Actionable recommendations

What it provides: A list of concrete, specific action items that the SPM can execute to address the identified issues. Generated by the LLM based on the full evaluation context.

Examples:

  • "Update article KB12345 to include troubleshooting steps for error code 0x80040305"
  • "Create new article covering Exchange Online hybrid mail flow configuration for E3 plans"
  • "Replace citation with a more relevant article addressing Azure AD Connect sync failures"
  • "Add step-by-step screenshots for the updated admin center UI"

CSV format: Multiple actions are separated by ; in the CSV output column synthesis_pm_actions.

Escalation Detection Patterns

The agent scans issue text for 13+ regex patterns indicating customer frustration:

escalat(e|ed|ion) transfer me/this speak to a manager need a specialist unacceptable Nth time calling already contacted support previous case SLA breach business is stopped critical deadline executive sponsor VP is asking

If ≥ 2 escalation signals are detected, the transfer reason is immediately classified as customer_escalation.

Data Models: CitationQualityResult & ResponseQualityResult

Two new dataclasses introduced by the mweaeval pipeline:

CitationQualityResult

overall_grounding_score per_citation_verdicts cited_percentage uncited_percentage

Each entry in per_citation_verdicts contains: url, verdict (good | partial | bad), score (0–100), and reasoning.

ResponseQualityResult

ai_response_quality_score response_quality_score groundedness_score issue_resolution_score verdict

The composite ai_response_quality_score is computed as: response_quality × 0.40 + groundedness × 0.30 + issue_resolution × 0.30. Verdict thresholds: excellent (≥80), good (60–79), fair (40–59), poor (<40).
